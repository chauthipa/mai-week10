# แบบออกแบบระบบติดตามงานทีม

เอกสารนี้ใช้คู่กับ [แผนโครงการ](plan.md) และ [ข้อกำหนด](requirements.md) พัฒนาตามลำดับ US-1 ถึง US-4 สำหรับระบบหลัก แล้วต่อด้วย US-5 และ US-6 สำหรับงานเสริม

เว็บใช้ Next.js App Router (ระบบจัดหน้าตามโฟลเดอร์), TypeScript และ Tailwind บน Vercel ส่วน Supabase Auth จัดการบัญชีและการเข้าสู่ระบบ และ Postgres เก็บข้อมูลพร้อม RLS (กฎกำหนดสิทธิ์ทีละแถว)

## แบบข้อมูล

PK คือรหัสหลักประจำแถว, FK คือคอลัมน์ที่ต้องอ้างถึงแถวที่มีอยู่, UNIQUE คือค่าที่ห้ามซ้ำ และ CHECK คือกฎตรวจค่าก่อนบันทึก คอลัมน์เป็น `NOT NULL` เว้นแต่ระบุว่าเว้นว่างได้

| ตาราง | คอลัมน์ | ชนิด | กฎหรือความหมาย |
| --- | --- | --- | --- |
| `profiles` | `user_id` | `uuid` | PK, FK → `auth.users.id` หนึ่งโปรไฟล์ต่อหนึ่งบัญชี |
| `profiles` | `display_name` | `text` | ชื่อที่แสดง หลังตัดช่องว่างหัวท้ายต้องมีข้อความ |
| `profiles` | `email` | `text` | อีเมลจากบัญชีใน Supabase Auth ใช้ส่งอีเมลใน US-6 |
| `teams` | `id` | `uuid` | PK สุ่มในฐานข้อมูล |
| `teams` | `name` | `text` | ชื่อทีม หลังตัดช่องว่างหัวท้ายต้องมีข้อความ |
| `teams` | `invite_code` | `text` | UNIQUE และ CHECK ให้เป็นอักษรอังกฤษตัวใหญ่ 6 ตัว สุ่มในฐานข้อมูล |
| `team_members` | `user_id` | `uuid` | PK, FK → `profiles.user_id` บังคับให้ผู้ใช้หนึ่งคนอยู่ได้หนึ่งทีม |
| `team_members` | `team_id` | `uuid` | FK → `teams.id` และ UNIQUE ร่วมกับ `user_id` เพื่อให้งานอ้างถึงสมาชิกในทีมเดียวกันได้ |
| `team_members` | `role` | `text` | CHECK ให้เป็น `leader` (หัวหน้า) หรือ `member` (สมาชิก) และใช้ดัชนี UNIQUE เฉพาะแถว `leader` ให้แต่ละทีมมีหัวหน้าได้คนเดียว |
| `tasks` | `id` | `uuid` | PK สุ่มในฐานข้อมูล |
| `tasks` | `team_id` | `uuid` | FK → `teams.id` เป็นทีมเจ้าของงาน |
| `tasks` | `assignee_id` | `uuid` | ผู้รับงานหนึ่งคน คู่ `(team_id, assignee_id)` เป็น FK → `team_members(team_id, user_id)` |
| `tasks` | `created_by` | `uuid` | ผู้สร้างงาน ฐานข้อมูลตรวจว่าตรงกับบัญชีที่ส่งคำขอ คู่ `(team_id, created_by)` เป็น FK → `team_members(team_id, user_id)` |
| `tasks` | `title` | `text` | ชื่องาน หลังตัดช่องว่างหัวท้ายต้องมีข้อความ |
| `tasks` | `description` | `text` | รายละเอียด เว้นว่างได้ |
| `tasks` | `due_date` | `date` | วันกำหนดส่ง เว้นว่างได้ เก็บเป็นวันที่โดยไม่มีเวลา |
| `tasks` | `status` | `text` | ค่าเริ่มต้น `todo` และ CHECK ให้เป็น `todo` (ยังไม่เริ่ม), `in_progress` (กำลังทำ) หรือ `done` (เสร็จแล้ว) |
| `tasks` | `created_at` | `timestamptz` | เวลาที่สร้าง ให้ฐานข้อมูลกำหนด |

`auth.users` เป็นตารางบัญชีที่ Supabase ดูแล เว็บใช้ผ่าน Auth API ส่วนตารางทั้งสี่ข้างต้นอยู่ใน `public` และเปิด RLS ตาม NFR-1

## ตารางสิทธิ์สำหรับ RLS

`select` = อ่าน, `insert` = เพิ่ม, `update` = แก้, `delete` = ลบ สิทธิ์ในตารางนี้ใช้กับคำขอจากเว็บและ API ที่ใช้ publishable key (กุญแจสำหรับเรียก Supabase ภายใต้สิทธิ์ของผู้ใช้) โดย `anon` คือผู้ที่ยังไม่ล็อกอิน และคนนอกทีมรวมบัญชีที่ยังไม่มีทีมด้วย

| ตาราง | บทบาทต่อข้อมูลแถวนั้น | `select` | `insert` | `update` | `delete` |
| --- | --- | --- | --- | --- | --- |
| `profiles` | เจ้าของโปรไฟล์ แม้ยังไม่มีทีม | อ่านของตัวเอง | — | — | — |
| `profiles` | หัวหน้าหรือสมาชิกทีมเดียวกัน | อ่านชื่อและอีเมลของเพื่อนร่วมทีม | — | — | — |
| `profiles` | คนนอกทีม หรือ `anon` | — | — | — | — |
| `teams` | หัวหน้าหรือสมาชิกทีม | อ่านทีมของตน รวมรหัสเชิญ | — | — | — |
| `teams` | คนนอกทีม หรือ `anon` | — | — | — | — |
| `team_members` | หัวหน้าหรือสมาชิกทีม | อ่านรายชื่อและบทบาทในทีมของตน | — | — | — |
| `team_members` | คนนอกทีม หรือ `anon` | — | — | — | — |
| `tasks` | หัวหน้าทีมเจ้าของงาน | อ่านทุกงานในทีม | สร้างในทีมตน | แก้สถานะและข้อมูลงานในทีม | — |
| `tasks` | สมาชิกทีมที่เป็นผู้รับงาน | อ่านงานในทีม | — | แก้เฉพาะ `status` ของงานที่ตนรับ | — |
| `tasks` | สมาชิกทีมที่ไม่ได้รับงานแถวนั้น | อ่านงานในทีม | — | — | — |
| `tasks` | คนนอกทีม หรือ `anon` | — | — | — | — |

หัวหน้าปรับชื่องาน รายละเอียด วันกำหนดส่ง ผู้รับงานในทีม และสถานะได้ตามสิทธิ์ฐานข้อมูล หน้าเว็บเปิดให้เปลี่ยนสถานะตาม US-4 การลบงานตามแผนทำจาก Supabase Table Editor โดยผู้ที่ได้รับสิทธิ์ผู้ดูแลโครงการ Supabase ซึ่งเป็นสิทธิ์คนละชุดกับบทบาทหัวหน้าทีมในเว็บ

กฎอ่าน `teams`, `team_members` และ `tasks` เทียบทีมของแถวกับทีมปัจจุบันของผู้เรียก ส่วน `profiles` อนุญาตเมื่อเป็นแถวของผู้เรียกเอง หรือพบเจ้าของโปรไฟล์ใน `team_members` ของทีมเดียวกัน ให้สิทธิ์ระดับตารางแก่ `authenticated` เฉพาะการกระทำที่จำเป็นตามตารางสิทธิ์ข้างต้น และให้ RLS ตรวจซ้ำว่าใช้สิทธิ์กับแถวใดได้

## ฟังก์ชันฐานข้อมูลและกติกาที่บังคับใช้

ฟังก์ชัน `SECURITY DEFINER` คือคำสั่งที่ทำงานด้วยสิทธิ์ของเจ้าของฟังก์ชัน ใช้เฉพาะจุดที่ต้องข้ามข้อจำกัดการอ่านหรือเขียนของผู้เรียก ฟังก์ชันกำหนด `search_path` แบบตายตัว ระบุชื่อตารางพร้อมชื่อกลุ่มตาราง และปิดสิทธิ์เรียกเริ่มต้นของ `PUBLIC` กับ `anon` เปิดสิทธิ์ให้ `authenticated` (ผู้ล็อกอินแล้ว) เฉพาะฟังก์ชันที่ตั้งใจให้เรียกตามด้านล่าง

| ฟังก์ชัน | ทำอะไร | อ้างอิง |
| --- | --- | --- |
| `sync_auth_profile()` | ทำงานอัตโนมัติจาก Supabase Auth ตอนสร้างบัญชี ดึงชื่อจากข้อมูลสมัครที่ผ่านการตรวจ และคัดลอกอีเมลจากแถวบัญชี ซิงก์อีเมลเมื่อบัญชีเปลี่ยนอีเมล ให้สิทธิ์เรียกผ่านตัวทำงานอัตโนมัติของฐานข้อมูลเท่านั้น | AC-1.1, AC-6.4 |
| `private.current_team_id()`, `private.is_team_leader(team_id)` | อ่านสมาชิกภาพจาก `auth.uid()` (รหัสบัญชีที่ยืนยันแล้ว) คืนทีมของผู้เรียกหรือผลใช่/ไม่ใช่ ให้ RLS ใช้โดยไม่วนกลับไปเรียกกฎของ `team_members` ซ้ำ เก็บใน `private` ซึ่งอยู่นอก API ที่เปิดให้เว็บเรียก | AC-2.6, AC-3.3, AC-3.7, AC-4.2–AC-4.4 |
| `create_team(name)` | ตรวจว่าผู้เรียกยังไม่มีทีมและชื่อตัดช่องว่างแล้วไม่ว่าง สุ่มรหัสเชิญ เกิดรหัสซ้ำให้สุ่มใหม่ สร้างทีมและบันทึกผู้เรียกเป็น `leader` ในธุรกรรมเดียว (สำเร็จหรือย้อนกลับพร้อมกัน) คืนเฉพาะรหัสประจำทีมที่สร้าง | AC-2.1, AC-2.2, AC-2.4, AC-2.5 |
| `join_team(invite_code)` | ตรวจว่าผู้เรียกยังไม่มีทีม ตัดช่องว่างและแปลงรหัสเป็นตัวใหญ่ก่อนตรวจ บันทึกผู้เรียกเป็น `member` เมื่อรหัสตรง แล้วคืนเฉพาะรหัสประจำทีมหลังเข้าร่วม ถ้ารหัสผิดหรือไม่พบทีม ให้ผลสำหรับข้อความ “ไม่พบทีมจากรหัสนี้” | AC-2.1, AC-2.3, AC-2.4, AC-2.6 |

- **สมาชิกภาพ (AC-2.2–AC-2.4)** ทั้งสองฟังก์ชันผูกคำขอกับ `auth.uid()` ฐานข้อมูลใช้ PK ของ `team_members.user_id` รับมือเมื่อบัญชีเดียวส่งคำขอพร้อมกัน แปลงกรณีนี้เป็น “คุณมีทีมอยู่แล้ว” และย้อนการสร้างทีมที่แพ้การบันทึก หน้า `/team` อ่านรายละเอียดผ่าน RLS หลังได้สมาชิกภาพแล้ว
- **การสร้างงาน (AC-3.1, AC-3.3–AC-3.5)** กฎ `insert` ตรวจว่าผู้เรียกเป็นหัวหน้าของ `team_id` และ `created_by` ตรงกับ `auth.uid()` ให้ฐานข้อมูลกำหนดผู้สร้างและบังคับว่างานใหม่เริ่มที่ `todo` แม้มีการส่งสถานะอื่นมา FK แบบคู่กันตรวจว่าผู้รับงานอยู่ทีมเดียวกันทั้งตอนสร้างและตอนแก้ผู้รับงาน ชื่อที่ว่างหลังตัดช่องว่างถูกปฏิเสธและเว็บแสดง “กรุณากรอกชื่องาน”
- **การเปลี่ยนสถานะและข้อมูล (AC-4.1–AC-4.4)** กฎ `update` ตรวจสิทธิ์ของผู้เรียกกับแถวเดิม (`USING`) และแถวที่จะบันทึก (`WITH CHECK`) ส่วน trigger (คำสั่งอัตโนมัติก่อนบันทึก) เทียบค่าเดิมกับค่าใหม่ ผู้รับงานที่เป็นสมาชิกแก้ได้เฉพาะ `status` ส่วนหัวหน้าแก้ช่องข้อมูลงานตามตารางสิทธิ์ ทั้งสองบทบาทแก้ `id`, `team_id`, `created_by` และ `created_at` ไม่ได้ การส่งสถานะพร้อมแก้ช่องที่ไม่มีสิทธิ์จะถูกปฏิเสธทั้งคำขอ สถานะเปลี่ยนไปค่าใดในสามค่าได้ตาม AC-4.1

## หน้าจอและการทำงาน

| เส้นทาง | หน้าจอและผลที่ต้องเห็น | อ้างอิง |
| --- | --- | --- |
| `/login` | มีทางเลือกสมัครและล็อกอิน การสมัครกรอกชื่อที่แสดง อีเมล และรหัสผ่านอย่างน้อย 6 ตัว ตรวจข้อมูลทั้งฝั่งเว็บและฝั่งเซิร์ฟเวอร์ สมัครหรือล็อกอินสำเร็จไป `/team` ใน workshop ที่ปิดการยืนยันอีเมล รหัสผ่านผิดแสดง “อีเมลหรือรหัสผ่านไม่ถูกต้อง” และอยู่หน้าเดิม | US-1, AC-1.1, AC-1.2 |
| แถบด้านบนและหน้าที่ต้องล็อกอิน | แถบบนแสดงชื่อจาก `profiles` และปุ่มออกจากระบบ เมื่อออกจากระบบให้ล้างสถานะการเข้าใช้และกลับ `/login` ใช้คุกกี้ที่คงอยู่เมื่อเปิดเบราว์เซอร์ใหม่และใช้ `proxy.ts` ต่ออายุสถานะการเข้าใช้ หน้า `/team`, `/tasks`, `/my` ส่งผู้ที่ยังไม่ล็อกอินไป `/login` | US-1, AC-1.3–AC-1.5 |
| `/team` | คนที่ยังไม่มีทีมเห็นฟอร์ม “สร้างทีม” และ “เข้าร่วมทีม” ถ้าชื่อว่างแสดง “กรุณากรอกชื่อทีม” ผู้ที่มีทีมเห็นชื่อทีม รหัสเชิญ 6 ตัว และชื่อสมาชิกพร้อมบทบาทหัวหน้าหรือสมาชิก | US-2, AC-2.1–AC-2.6 |
| `/tasks` | คนที่ยังไม่มีทีมไป `/team` สมาชิกเห็นงานในทีมสามคอลัมน์ “ยังไม่เริ่ม / กำลังทำ / เสร็จแล้ว” การ์ดแสดงชื่องาน ผู้รับงาน และวันกำหนดส่งแบบไทยเมื่อมี หากไม่มีงานแสดง “ยังไม่มีงานในทีม” | US-3, AC-3.2, AC-3.6, AC-3.7 |
| `/tasks` สำหรับสร้างงาน | เฉพาะหัวหน้าเห็นฟอร์ม ชื่องานเป็นช่องบังคับ รายละเอียดและวันกำหนดส่งเว้นได้ รายชื่อผู้รับงานมาจากสมาชิกในทีมและรวมหัวหน้า ส่งสำเร็จให้โหลดรายการใหม่และแสดงงานในคอลัมน์ “ยังไม่เริ่ม” | US-3, AC-3.1, AC-3.3–AC-3.5 |
| `/tasks` สำหรับเปลี่ยนสถานะ | หัวหน้าเห็นตัวเลือกในทุกการ์ด ผู้รับงานทั่วไปเห็นเฉพาะการ์ดของตัวเอง เมื่อบันทึกสำเร็จให้โหลดรายการล่าสุดและย้ายการ์ดทันที ถ้าบันทึกไม่ผ่านให้คงข้อมูลเดิมและแสดงข้อความไทย | US-4, AC-4.1–AC-4.4 |
| `/my` (งานเสริม) | แสดงเฉพาะงานที่ผู้ใช้เป็นผู้รับ เรียงวันกำหนดส่งจากวันก่อนมาวันหลัง โดยรายการไม่มีกำหนดอยู่ท้าย ซ่อนงานเสร็จแล้วเมื่อเปิดหน้าและมีตัวเลือก “แสดงงานที่เสร็จแล้ว” ถ้าไม่มีงานที่ได้รับมอบหมายให้แสดง “ยังไม่มีงานที่ได้รับมอบหมาย” พร้อมลิงก์ `/tasks` ถ้ามีแต่งานเสร็จแล้วให้แสดงข้อความตามตัวกรองและคงตัวเลือกไว้ ใช้การเปลี่ยนสถานะเดียวกับ `/tasks` | US-5, AC-5.1–AC-5.4 |

- **วันกำหนดส่ง (AC-3.2, AC-4.5)** เปรียบเทียบวันที่ปัจจุบันใน `Asia/Bangkok` กับ `due_date` โดยตรง แสดงป้ายสีแดง “เลยกำหนด” เมื่อ `due_date` น้อยกว่าวันนี้และสถานะยังไม่เป็น `done` ใช้กติกาเดียวกันทุกหน้าที่แสดงการ์ดงาน
- **การตรวจสิทธิ์ (AC-1.5, AC-2.6, AC-3.7, NFR-1–NFR-2)** ใช้ตัวเชื่อม Supabase ใน `lib/supabase/server.ts` และ `lib/supabase/client.ts` ตามฝั่งที่ทำงาน ทุกหน้าที่ต้องล็อกอินและทุกคำสั่งเปลี่ยนข้อมูลฝั่งเซิร์ฟเวอร์ตรวจผู้ใช้ด้วย `supabase.auth.getUser()` หรือ `getClaims()` ก่อนใช้สิทธิ์บัญชีนั้น รับจากฟอร์มเฉพาะข้อมูลที่จำเป็น เช่น ผู้รับงานที่เลือก โดยฐานข้อมูลตรวจสมาชิกภาพซ้ำ ใช้ `NEXT_PUBLIC_SUPABASE_URL` และ `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` สำหรับ Supabase
- **การแสดงผล (NFR-3–NFR-4)** แต่ละหน้าใช้ข้อความไทยระหว่างโหลด เมื่อไม่มีข้อมูล และเมื่อผิดพลาด สำหรับหน้าที่เป็นฟอร์ม ให้แสดงสถานะระหว่างส่ง คุณสมบัติของข้อมูลที่ต้องกรอก และผลเมื่อส่งไม่ผ่าน ที่ความกว้าง 375 พิกเซลให้คอลัมน์งานเรียงลงมาและตัดบรรทัดข้อความยาวได้ เพื่อให้ใช้งานโดยไม่ต้องเลื่อนซ้ายขวา

## อีเมลแจ้งมอบหมาย (US-6 งานเสริม)

1. ใช้คำสั่งฝั่งเซิร์ฟเวอร์ที่รับฟอร์ม `/tasks` บันทึกงานด้วยสิทธิ์ของหัวหน้าที่ล็อกอินก่อน ถ้าบันทึกไม่สำเร็จให้จบคำขอโดยไม่ส่งอีเมล (AC-6.2)
2. เมื่อบันทึกสำเร็จ ใช้ข้อมูลของงานที่ฐานข้อมูลคืนมาอ่านอีเมลจาก `profiles` ด้วย `assignee_id` ของแถวที่บันทึก รวมทั้งชื่อทีมและชื่อผู้มอบหมายจาก `team_id` และ `created_by` ตามลำดับ ช่องข้อมูลจากฟอร์มมีเฉพาะข้อมูลที่ใช้สร้างงาน (AC-6.4)
3. ส่งผ่าน Gmail SMTP (บริการส่งอีเมล) ทันทีในคำขอเดียว หัวเรื่อง `งานใหม่: <ชื่องาน>` เนื้อหามีชื่องาน ชื่อทีม ชื่อผู้มอบหมาย และวันกำหนดส่ง หรือ “ไม่มีกำหนด” ตั้งเวลารอการส่งให้สั้นกว่าหนึ่งนาที และตรวจกล่องขาเข้าจริงเพื่อยืนยันเกณฑ์ภายในหนึ่งนาที (AC-6.1)
4. ถ้าอ่านข้อมูลสำหรับส่งไม่ได้ ส่งไม่สำเร็จ หรือหมดเวลารอ ให้คงงานที่สร้างไว้ รีเฟรชรายการ และแสดง “สร้างงานแล้ว แต่ส่งอีเมลแจ้งไม่สำเร็จ” (AC-6.3)
5. ใช้ `GMAIL_USER` และ `GMAIL_APP_PASSWORD` ของบัญชี Gmail สำหรับ workshop ฝั่งเซิร์ฟเวอร์เท่านั้น เก็บค่าใน `.env.local` สำหรับเครื่องผู้เรียน และ Environment Variables ของ Vercel สำหรับเว็บที่เผยแพร่ (AC-6.5, NFR-2)

## ตรวจความพร้อมก่อนส่งแต่ละเรื่อง

- ใช้บัญชี A/B/C ตาม [ข้อกำหนด](requirements.md) ตรวจว่าหัวหน้า A สร้างงานในทีมให้ B ได้, B เปลี่ยนได้เฉพาะสถานะงานของตน, และ C อ่านทีม สมาชิก โปรไฟล์ และงานของทีม A ไม่ได้ ตรวจทั้งหน้าเว็บและคำขอ Supabase ด้วยสิทธิ์ของบัญชีทดสอบ เพิ่มกรณีบัญชีที่ยังไม่มีทีมและผู้ที่ยังไม่ล็อกอิน (AC-1.5, AC-2.6, AC-3.3, AC-3.4, AC-3.7, AC-4.3, AC-4.4)
- ทดสอบคำขอสร้างหรือเข้าร่วมทีมพร้อมกันจากบัญชีเดียว ตรวจว่าเหลือสมาชิกภาพเดียวและไม่มีทีมที่สร้างค้างโดยไม่มีหัวหน้า ใช้วันกำหนดส่งเมื่อวาน วันนี้ และงานที่เสร็จแล้วเพื่อเช็กการแสดงป้ายตามเวลาไทย (AC-2.4, AC-4.5)
- เมื่อพัฒนาเสร็จแต่ละเรื่อง ใช้ `npm run lint` ตรวจรูปแบบและปัญหาในโค้ด, `npm run build` ตรวจว่าเตรียมเว็บสำหรับเผยแพร่ได้ และทดสอบหน้าจอกว้าง 375 พิกเซล พร้อมตรวจทุก AC ของเรื่องนั้น (NFR-3, NFR-4)
